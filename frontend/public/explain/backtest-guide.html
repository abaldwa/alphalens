Running & reading backtests

A working reference for the two backtest engines, how strategy_id is codified and horizon_bucket defaulted automatically, when a plain backtest is enough versus when you need Walk-Forward, how to queue several strategies to run unattended, and a full breakdown of the 42 Technical screener templates — including which ones are quick trades and which are position trades.

01

How to use the Backtest module

There are two engines under backtest/, and which one you reach for depends on what you're testing:

ML engine

backtest/engine.py's BacktestEngine — the Signal5D/21D/63D + MetaLabeler + Exit-model stack. Driven by run_phase1_backtest.py / run_phase2_backtest.py / run_phase3_backtest.py, or all three together via run_batch_backtest.py (sequenced light-to-heavy with an OOM guard). run_iterative_backtest.py sits on top of this engine to iteratively retrain the MetaLabeler.

Orchestrator

backtest/core/engine.py's BacktestOrchestrator — the channel-agnostic engine for Technical, Fundamental, and Momentum screener/rotation strategies. Driven by run_orchestrator_backtest.py, or triggered straight from the Backtest page's "Run a Backtest" panel in the UI.

From the command line

# ML engine — one phase
python3 -m backtest.run_phase1_backtest --folds 5 --trials 5

# ML engine — all three phases, sequenced to avoid OOM
python3 -m backtest.run_batch_backtest --phases 1 2 3

# ML engine — iteratively retrain the MetaLabeler, holdout-evaluated once
python3 -m backtest.run_iterative_backtest --horizon-days 5 --folds 4

# Orchestrator — Technical channel, Minervini SEPA (E2), top 10.
# strategy_id and horizon-bucket are both OPTIONAL — omitted, they're
# codified/defaulted for you (see §2 below): this becomes
# strategy_id = ta_e2_63d_20260722, horizon_bucket = 63_day.
python3 -m backtest.run_orchestrator_backtest \
  --channel technical --template-name E2 --top-n 10 \
  --start-date 2023-01-01 --end-date 2026-07-01

Scheduling several strategies sequentially

run_strategy_queue.py takes a queue of jobs — backtests and/or an iterative retrain — and runs them one after another, memory-gated between each (the same subprocess-isolation pattern run_batch_backtest.py already uses, shared via backtest/batch_common.py). Point it at a queue once instead of triggering each strategy by hand and waiting between them:

{
  "jobs": [
    {"kind": "orchestrator", "channel": "technical", "template_name": "E2", "top_n": 10,
     "start_date": "2023-01-01", "end_date": "2026-07-01"},
    {"kind": "orchestrator", "channel": "technical", "template_name": "B1", "top_n": 10,
     "start_date": "2023-01-01", "end_date": "2026-07-01"},
    {"kind": "iterative_retrain", "horizon_days": 5, "folds": 4}
  ]
}
python3 -m backtest.run_strategy_queue --queue-file my_queue.json

Each job's strategy_id/horizon_bucket defaults exactly as a standalone run_orchestrator_backtest.py call would (they're genuinely optional per job, not required just because they're in a queue) — the queue runner doesn't re-implement that defaulting, it only sequences.

From the UI

The Backtest page (/backtest) has four panels beneath the Runs table:

Runs

Filterable list across every channel/mode, with per-run fold metrics, lineage (parent → child re-runs), and the feature-log inspector (every candidate considered, not just the ones traded).

Run a Backtest

Triggers run_orchestrator_backtest.py as a background job — pick a channel, date range, and the channel-specific field (screener template, screener preset, or lookback months). Strategy ID and horizon default automatically — both stay editable if you want to override them. Polls until done, then the run appears above.

Schedule a Strategy Queue

Build a list of strategies (and optionally an iterative retrain) right in the page, then submit the whole queue — it runs sequentially in the background, one consolidated status to poll instead of babysitting each trigger.

Iterative Retrain

Triggers the MetaLabeler retrain loop — shows the holdout fiscal year chosen, every tuning iteration's Sharpe/DSR/random-feature-test result, and the one-shot holdout evaluation.

Every path writes to the same place: every run — CLI, queued, or UI-triggered — lands in the backtest_runs table via save_run_result(), so GET /api/v1/backtest/runs and the Runs table always show the full picture regardless of how a run was started.

02

What goes in strategy_id

strategy_id is now a codified, machine-generated label by default (backtest/strategy_id.py) rather than something you invent by hand each time — the format bakes the run date in, so you can recover "when was this triggered" straight from the string, no DB lookup needed. It's still overridable per run if you want a custom label instead.

The canonical format

{channel}_{descriptor}_{horizon_code}_{YYYYMMDD}
channel
ta (technical) · fund (fundamental) · mom (momentum)
descriptor
the screener template name, the screener preset name, or top{N}_{lookback}m for momentum
horizon_code
5d · 21d · 63d · 1y · mb · cust
YYYYMMDD
the date this run was triggered

Example: triggering E2 (Trend Following → 63-day, see §4) on 22 July 2026 produces ta_e2_63d_20260722 automatically — no channel, template, horizon, or date needs to be typed twice.

Getting the date back out

from backtest.strategy_id import parse_strategy_id

parsed = parse_strategy_id("ta_e2_63d_20260722")
parsed.channel         # "technical"
parsed.descriptor      # "e2"
parsed.horizon_bucket  # HorizonBucket.D63
parsed.run_date        # date(2026, 7, 22)

Naming convention, not a uniqueness key: backtest_runs.run_id (a uuid) is still the real primary key — two runs of the identical strategy on the identical day legitimately share a strategy_id, the same way an unchanged scheduled job producing the same label twice is correct, not a collision. A strategy_id from before this convention existed (e.g. signal_5d_metalabeler_retrain) is real historical data, not something parse_strategy_id() is expected to understand — it raises rather than guess.

03

Backtest vs Walk-Forward

Both are BacktestRun.mode values the same BacktestOrchestrator executes — the difference is entirely about whether anything gets retrained mid-run.

mode = backtest

One pass over the whole window. No mid-run refitting — the adapter's rule (a screener template, a screener preset, a rotation rule) is fixed for the entire backtest.

Use this for: Technical, Fundamental, and Momentum channel runs today — none of their adapters implement a refit() method, so there's nothing to retrain. This is also what run_orchestrator_backtest.py always uses.

mode = walk_forward

Routed through WalkForwardRunner, which calls adapter.refit(as_of_date) at a cadence (the horizon bucket's default rebalance cadence, unless overridden) — an expanding-window retrain loop.

Use this for: a model-based adapter that actually needs periodic retraining. The hook exists and is exercised in tests, but no shipped Technical/Fundamental/Momentum adapter implements refit() yet — it's ready for the next ML-style adapter, not a knob to flip on today's rule-based screeners (flipping it for them is a harmless no-op, not an error, but it does nothing).

Not the same thing as the ML engine's own fold retraining: run_phase1/2/3_backtest.py's BacktestEngine already retrains its Signal model and MetaLabeler every fiscal-year fold internally (via WalkForwardValidator) — that's a separate, always-on mechanism specific to that engine, independent of the mode flag described here.

Technical strategy reference

All 42 pre-built screener templates (systems/technical_analysis/screener/templates.py), grouped by style. Horizon below is what run_orchestrator_backtest.py actually defaults horizon_bucket to when you don't specify one (backtest/strategy_id.py's default_horizon_for_technical()) — not enforced by the template itself, so you can still override it per run; this is just what happens automatically if you don't.

Mean Reversion
Oversold bounce — the edge decays fast. Defaults to 5_day.
Momentum
