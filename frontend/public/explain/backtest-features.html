Pipeline

Where features come from

Backtest and Walk-Forward don't compute a separate, lighter feature set for speed — they read the same daily Parquet matrix the live pipeline writes, which is the entire point: a backtest is only honest if it sees what production would actually have seen on that date.

  1. Ingestion — bhavcopy, F&O, macro, fundamentals, shareholding, MF holdings land in the DataStore (DuckDB + Parquet), corporate-action adjusted before anything downstream touches them.
  2. Per-category computation — each features/*.py module computes one category, vectorized across all stocks (never a Python loop per ticker).
  3. Assembly — features/matrix_builder.py joins every category into one row per (ticker, date) and writes datastore/features/daily/YYYY-MM-DD.parquet.
  4. Registry — features/registry.py's FEATURE_REGISTRY is the single source of truth for every feature's category, data source, update frequency, and PIT rule — new features register here, they don't get bolted on ad hoc.
  5. Backtest / Walk-Forward read — WalkForwardBacktester and the channel adapters load this same matrix, filtered to date < test_year for training folds and the fold's own year for testing — never a random split.
  6. Paper trading reads the same matrix for "today" only, via a live adapter — no separate feature path exists for forward-testing either.
Non-negotiable

Point-in-time rules

The single biggest source of an inflated, untrustworthy backtest is a feature that leaks information from after the decision date. Every category below is joined on the date it was actually knowable, not the date it describes.

OHLCV / Technical
Always knowable same-day; must be corporate-action adjusted first — raw bhavcopy prices corrupt every moving-average and momentum feature
Fundamentals
Joined on announcement_date, never quarter_end_date
Shareholding / Governance
Joined on filing_date — available ~21 days after quarter end
MF Holdings
Available ~5th of the following month; that date is what's used, not the holding-period end
Option Chain
3:25 PM daily scrape — non-recoverable if missed, F&O features go to NaN rather than being backfilled from a later snapshot
Delisted stocks
Included throughout, with forced exits at last traded price — omitting them would survivorship-bias every result

Every feature — regardless of phase or category — is registered in features/registry.py's FEATURE_REGISTRY with its category, data source, update frequency, and PIT rule, so the backtest engine (and integrity_checker.py) can programmatically confirm no feature is being joined ahead of when it was actually knowable.
Feedback loop

Per-decision feature logging

A summary metric like CAGR tells you the strategy worked; it doesn't tell you why a specific stock was skipped or which features drove a losing trade. backtest/core/feature_log.py exists to answer that.

Every run — Backtest, Walk-Forward, or Paper Trading — can write one row per (run_id, ticker, as_of_date) to the backtest_feature_log DuckDB table, covering every candidate the strategy considered, not just the ones it acted on:

backtest_feature_log schema
ColumnContents
run_id / parent_run_idWhich run wrote this row, and — for a what-if re-run — which run it was compared against
ticker / as_of_dateThe stock and date the decision was made for
horizon_bucket5-day / 21-day / 63-day / 1-year / MultiBagger / custom
feature_vector_jsonThe full feature row the adapter saw at decision time — every category above, as available on that date
signal_outputWhat the model/rule actually returned
decision_takenbought / held / sold / skipped_no_cash / skipped_sector_cap — the portfolio-level outcome, not just the raw signal

Writes are buffered and flushed in batches of 5,000 (a single 20-year Walk-Forward run can generate millions of rows across thousands of tickers and hundreds of rebalance dates), and the table has an upsert key on (run_id, ticker, as_of_date) so a re-run of the same decision overwrites rather than duplicates.

# the read side of the feedback loop — a researcher finding losing trades
rows = query_feature_log(conn, run_id="backtest_2026-07-20_technical_21d")
losers = [r for r in rows if r["decision_taken"] == "sold" and ...]
# -> re-engineer features / retrain offline -> rerun with a new run_id
#    carrying parent_run_id, so the UI can render "compare to parent run"
Status: core/feature_log.py and its DuckDB schema are implemented. The consumer side — a UI that queries backtest_feature_log and renders a parent/child run comparison — is part of the still-in-progress Unified Backtest & Paper Trading Umbrella, not yet wired into a dashboard screen.
