Architecture

One backtest module, every kind of trade

There is exactly one Backtest module in AlphaLens. It does not fork by strategy type — Technical, Fundamental, ML, and Momentum all run through the same engine, the same portfolio and cost logic, and the same metrics.

Historically this wasn't true: backtest/engine.py grew to drive only the ML signal stack, momentum_backtest.py became a separate engine built the same week with its own CAGR methodology, Technical had nothing but a win-rate lookup (strategy_confidence.py), and Fundamental had no backtest capability at all. BacktestUmbrellaPlan.md is the confirmed plan to collapse that into one system:

Shared core, thin adapters per channel
LayerModuleShared across all 4 channels?
Run definitioncore/run_context.py — BacktestRun: channel, strategy_id, horizon_bucket, universe, date range, capital modeYes
Position sizingcore/horizon.py — one sizing table keyed by horizon bucket (5-day / 21-day / 63-day / 1-year / MultiBagger), not by channelYes
Portfolio & cash flowscore/portfolio.py — SIP injection, position sizing, cash tracking, sector/position capsYes
Costsbacktest/costs.py's IndianTransactionCostsYes — already shared, unchanged
Metricscore/metrics.py — CAGR, XIRR, drawdown, win rate, profit factor, churn, benchmark comparisonYes
Taxcore/tax.py — FY-end LTCG/STCG cash outflowYes
Signal generationadapters/{technical,fundamental,ml,momentum}_adapter.pyNo — this is the one channel-specific piece, behind a common StrategyAdapter contract

Every adapter implements the same two methods — generate_signals(universe, as_of_date, horizon_bucket) and feature_vector(ticker, as_of_date) — so the engine, portfolio, and metrics code never needs to know which channel it's running. adapters/ml_adapter.py is a thin wrapper around the existing, unmodified BacktestEngine rather than a rewrite, so the live /ml-backtest page keeps working unchanged throughout this migration.

Hard constraint: no cross-channel capital pooling, anywhere. Each strategy — a (channel, horizon-bucket) pair such as "Technical 21-day" or "Momentum MultiBagger" — runs its own independent backtest, walk-forward, and paper-trading cycle against its own dedicated capital base. core/portfolio.py is not allowed to grow a shared-pool concept, even later.
backtest/strategy_id.py

Strategy ID & horizon defaults

Every backtest, orchestrator trigger, and queued job carries a codified strategy_id instead of a hand-typed free-text label, so runs are identifiable and comparable by construction.

Format: {channel}_{descriptor}_{horizon_code}_{YYYYMMDD} — e.g. ta_e2_63d_20260722 is a Technical run of the E2 template at a 63-day horizon, launched 2026-07-22. parse_strategy_id() recovers channel, descriptor, horizon, and run date straight back out of the string, no database lookup required.

Horizon defaults by channel — used whenever horizon_bucket is left blank
ChannelKeyed byDefault
TechnicalTemplate style — see the strategy definitions pageMean Reversion → 5d · Momentum/Volatility → 21d · Trend Following → 63d
FundamentalScreener presetquality_compounder → 1y · garp / turnaround → 63d
MomentumLookback window≤3mo → 21d · ≤9mo → 63d · longer → 1y

Both strategy_id and horizon_bucket are optional on the CLI, the /orchestrator/trigger API, and the Backtest page's trigger panel — leave them blank and the backend resolves both from the table above. This is a naming convention, not a uniqueness key: older free-text ids (e.g. signal_5d_metalabeler_retrain) keep working unchanged.

Run several strategies unattended: run_strategy_queue.py (and the Backtest page's "Schedule a Strategy Queue" panel) chains multiple orchestrator/iterative-retrain jobs into one sequential, memory-gated submission — no manual re-triggering between runs.
Stage 1

Backtesting

Simulates a strategy against historical data before it ever touches a real signal. Walk-forward only — never a random train/test split on time-series data.

Where it lives

backtest/engine.py (WalkForwardBacktester) drives the ML signal stack today; momentum_backtest.py is a separate engine for Momentum; Technical has only strategy_confidence.py, a historical win-rate lookup rather than a full backtest; Fundamental has none yet. These four are being unified under backtest/core/ (shared engine, portfolio, metrics, tax) with thin per-channel adapters implementing one StrategyAdapter contract — see BacktestUmbrellaPlan.md.

How a run executes

  1. Fold split — expanding walk-forward folds: train on 2021 → test 2022; train 2021–22 → test 2023; and so on through the most recent year.
  2. Day-by-day simulation inside each fold, reproducing the live pipeline's exact order.
  3. P&D pre-filter blocks any ticker scoring above threshold before a buy signal is considered.
  4. Exit check on every held position — urgency > 80 exits today, 60–80 reduces by half.
  5. New buy signals generated and sized against sector/position caps.
  6. Cost model applied on every trade via IndianTransactionCosts — brokerage, STT, exchange fees, GST, stamp duty, and liquidity-scaled slippage (~0.40–0.50% round trip; small-cap slippage rises under ₹1Cr ADTV).
  7. Delisted stocks included throughout, so results aren't survivorship-biased.

Two further checks run over the result before it's trusted: integrity_checker.py screens for point-in-time leakage (e.g. a feature column that's secretly fundamentals-derived beyond its announcement date), and overfit_checks.py applies a Deflated Sharpe Ratio correction whenever 20+ configurations were tried, plus a random-feature shuffle test that a sound model should score ~50% on.

Robustness

What-if analysis

There's no separate "what-if" button — a what-if is just another backtest run with one input changed, compared against its parent. The mechanism that makes the comparison rigorous rather than anecdotal is the feature-vector log.

What can be varied

LeverWhere it livesExample what-if
Position sizingcore/horizon.py::sizing_for(bucket, overrides=...)"What if 21-day max position was 2% instead of 3% — does drawdown fall faster than CAGR?"
Transaction costsbacktest/costs.py::IndianTransactionCosts constructor args"What if slippage on small-caps was 0.50% instead of 0.30% — does the edge survive?"
Signal / meta thresholdsconfig/settings.py — SIGNAL_THRESHOLD, META_THRESHOLD"What if the buy threshold was 0.70 instead of 0.65 — fewer, higher-conviction trades?"
P&D / exit sensitivityconfig/settings.py — PND_BLOCK_THRESHOLD, EXIT_URGENT_THRESHOLD"What if exits triggered at urgency > 70 instead of 80 — does it clip winners early?"
Universe / date rangecore/run_context.py::BacktestRun"What if we only trade Tier-1 large caps — does churn and cost drag both drop?"
Capital modeBacktestRun.capital_mode (lump-sum vs. SIP)"What if capital arrived monthly instead of as one lump sum — how does XIRR change?"
Trial count correctionoverfit_checks.py::deflated_sharpe_ratio(n_trials=...)"What if we're honest that 40 configs were tried, not 5 — does the Sharpe survive DSR?"

How the comparison is made rigorous

Every run writes a full per-decision record to backtest_feature_log (DuckDB) via core/feature_log.py — not just the trades it took, but the feature vector, signal output, and decision (bought / held / skipped_no_cash / skipped_sector_cap / sold) for every candidate it considered, tagged with a run_id. A what-if run carries a parent_run_id back to the run it varied from, so a "compare to parent" query can isolate exactly which decisions flipped because of the changed input — not just that the aggregate CAGR moved.

Scope today: the levers above are real, overridable config, and the feature log is implemented (backtest/core/feature_log.py) — but a one-click "run a what-if grid and diff it" UI does not exist yet. Today, a what-if is: set the override, re-run with a fresh run_id + parent_run_id, then query backtest_feature_log and the metrics table for both runs.
Stage 2

Paper Trading

The bridge between backtest and live capital: real signals, generated for a real "today," against real prices — with a human in the loop and nothing at financial risk.

Where it lives

backtest/paper_trading/live_runner.py and approval_queue.py. Same StrategyAdapter contract the backtest uses, fed a live data source instead of a historical panel.

How a day runs

  1. Propose — PaperTradingRunner.propose_today() generates today's signals from the live adapter.
  2. Queue, never execute — every proposed buy/sell/forced-close is written to the pending-actions queue. Nothing touches the portfolio automatically.
  3. Human review — a person explicitly accept()s or reject()s each action.
  4. Reject → no state change. Accept → the trade executes against the persisted portfolio and the day counts toward Gate 7.
  5. Heartbeat on quiet days — even with zero trades, a row is logged so the day still counts as genuine operation.

Portfolio state persists to paper_trading/state/{channel}/{strategy_id}.json — cash, positions, trades, cash flows, and equity curve, one file per (channel, strategy) track.

The gate

Gate 7

The hard requirement standing between paper trading and real money.

Threshold
90 days
Current progress
0 / 90
Status
Not cleared

A strategy needs ≥90 distinct genuine forward-trading days of paper-trading history before it's eligible for live capital. The day count is anchored to an audit-proof invariant: one dated file (paper_trading/executions/{date}.csv) per day the bot actually ran — "CSV exists ⇔ bot genuinely ran." Nothing can retroactively backfill or fabricate a day.

Current state: paper trading is at 0 of 90 days. Historical replays (run_paper_trading_sim.py, which simulates 2007 and 2025 windows) do not count toward Gate 7 — they aren't real forward time, so this is the current bottleneck between AlphaLens and live-trading readiness.
Clarification

Forward testing is paper trading

AlphaLens doesn't have a separate forward-testing module — the terms describe the same stage from two angles.

"Paper trading" names how it runs (simulated capital, real signals, real prices). "Forward testing" names why it matters (proof the strategy holds up on data it couldn't have seen at backtest time, accumulated one real day at a time — as opposed to a historical replay). Gate 7 is the mechanism that enforces the forward-testing property: it only counts days that genuinely elapsed in real time, which is exactly what distinguishes forward testing from another backtest.
